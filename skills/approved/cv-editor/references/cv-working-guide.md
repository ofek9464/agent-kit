# CV working guide

Use only the sections relevant to the current request. The evidence record belongs in the candidate's project directory, never in the skill package. The examples below are fictional structures, not candidate facts.

## Reusable evidence record

For a substantial rewrite or repeated tailoring, maintain a compact Markdown record or another existing project format. Keep the complete verified experience here; the application CV contains the selection relevant to its audience. Do not create a parallel record if an adequate one already exists.

Useful fields are:

- Role, employer, dates, and the candidate's responsibilities.
- Project purpose, users or business domain, and an approved public description.
- Personal contribution, technologies, deployment context, and supported outcomes.
- Evidence source, confirmation status, and unresolved questions.
- Exact credentials, issuer, completion and expiration status.
- Preferred language, target roles, template, and saved artifact links.

Separate confirmed facts from questions and superseded claims. A later correction replaces the earlier claim; do not keep selecting from outdated wording. Keep internal names out of public descriptions when anonymity is requested, and avoid collecting unnecessary confidential details even in the private record.

Preserve the base when creating a tailored version. Use filenames or design titles that distinguish the candidate, role, and version. Keep a brief account of changed emphasis when useful for later updates; do not build an application tracker or send applications unless requested.

## Discover meaningful scale

Ask concrete questions about the work being described, using only the few that would materially improve it. For infrastructure work, possible topics include environments or services managed, deployment frequency, provisioning time, operational responsibility, and what manual work was replaced. For other roles, adapt the questions to the actual responsibilities.

For example: "For the deployment pipeline you built, what did a release involve before, and which steps did you automate?" This is more useful than asking the candidate to invent a percentage improvement.

Use measured figures or candidate-confirmed estimates with an explained basis and appropriate qualification. Do not infer savings, availability, or performance from the tools used, or convert an imprecise answer into an exact number. If scale is unknown, describe the supported accomplishment and purpose. A production deployment or enabling an internal workflow can be useful evidence without numerical results.

## Map a supplied job description

Distinguish explicit requirements from preferences. Build a compact internal mapping when tailoring would otherwise miss important evidence:

| Requirement | Importance in posting | Candidate evidence | Content decision |
| --- | --- | --- | --- |
| Infrastructure as code | Required | Confirmed provisioning project | Lead with the relevant contribution |
| Second cloud platform | Preferred | Training only | Keep under training if useful; do not imply production experience |
| On-call responsibility | Required | Not established | Ask if material; omit unsupported ownership |

Prioritize supported experience and reorder bullets or skill categories as needed. Preserve understandable career chronology. Use the posting's terminology when it accurately describes the work; keep technologies attached to the relevant contribution rather than repeating keywords mechanically.

Report evidence-backed strengths and gaps. Do not invent an ATS score, imply a real hiring system was tested, or use an arbitrary match percentage to tell the candidate not to apply.

## Check the delivered CV

Read the final artifact at normal viewing size. Can a quick scan identify the intended role, recent experience, strongest relevant contribution, and key technologies? If not, adjust emphasis or spacing within the chosen template. There is no universal rule that skills must precede experience, or that every CV must fit on one page.

Check contact details against the supplied source and verify that visible links point to the intended email address or professional profile. If authentication prevents checking a profile, verify the saved destination and disclose the access limitation instead of claiming the page was checked.

When delivering a PDF, extract its text with the available PDF tooling. Check that the candidate's name, contact details, headings, roles, dates, and revised passages survive extraction and appear in a coherent reading order. Pay particular attention to columns, sidebars, ligatures, and text turned into images. Compare the extracted text with the visual document; nonempty output alone is insufficient.

Repair extraction defects within the requested design where practical. If repair would require a substantial redesign, explain the specific defect and offer a separate simpler submission version while preserving the chosen original. Follow the application's requested file format. Do not describe a PDF as universally ATS-compatible merely because extraction succeeds.
