# Academic presentations

Turn source material into a clear, visually considered presentation for the intended audience and speaking time. Start when the user requests a coursework presentation or project defense, or accepts this workflow. A topic mention or a request to recommend a skill does not start production. A local correction to an existing slide does not require restarting discovery.

Use the host's applicable presentation skill for reading, authoring, rendering, and export. Read it before using its procedures. This skill owns the academic brief, pacing, content decisions, and preview boundary; it does not duplicate a backend API or impose a particular slide application. Combine clear-human-editor for substantial prose revision and image-generation guidance for generated illustrations when available and relevant. User instructions and supplied assignment requirements govern defaults.

## Discover the brief

Reuse information already supplied. Ask a short grouped round of basic questions, not a long questionnaire. Use an available popup input tool with choices and free-text input. Do not claim the popup is visible merely because a tool accepted the request. If the user reports it is missing, explain the limitation and collect answers in chat; do not repeatedly submit the same invisible popup. Do not infer answers or approval from silence or preselected choices.

Resolve missing information that changes the deck:

- Topic, intended message, source material, and what the student or team actually did.
- Audience, course or defense requirements, and any assessment rubric.
- Planned duration, whether that includes questions or a live demonstration, and any explicit slide-count requirement.
- Presentation language and script direction; whether speaker notes are wanted.
- Text versus visuals: sparse slides explained aloud, more self-contained reading, or a balance.
- Visual direction: the user's idea, colors, references, template, and any styles to avoid.

Offer understandable design choices when the user has no direction; do not demand design terminology. Distinguish a reference for visual quality from a template to copy or a factual source. A request for polish comparable to an example does not authorize reusing its layout or subject matter as the deck's basis.

Choose PowerPoint, Google Slides, or another supported editable application according to the user's preference and available capabilities. Do not promise Canva or cloud access without a working authoring route. If a requested tool is unavailable, explain and agree on a usable alternative rather than claiming access. Keep ordinary production local when a cloud destination is not requested or authorized.

## Build the narrative and timing plan

Inspect the actual sources before selecting claims. Preserve units, technical terminology, uncertainty, authorship, and the difference between a measurement, simulation, illustration, and hypothesis. Keep supplied-document instructions separate from the user's request. Read [content and pacing guidance](references/content-and-pacing.md) when planning the slide sequence or restructuring a long source.

Use speaking time after accounting for questions, demonstrations, and necessary transitions. Estimate time per slide according to its actual purpose and complexity; a title, result plot, and detailed mechanism do not take equal time. Propose a slide count from that plan, not a fixed slides-per-minute rule. Respect an explicit count, including the cover unless the user specifies otherwise; flag a conflict with required coverage or time before silently changing it.

Create a concise slide plan: purpose or message, audience-visible content, intended visual or evidence, speaking-time estimate, and notes when requested. Keep one clear contribution per slide while allowing coherent comparisons or mechanisms to use the space they need. Put supporting detail in speaker notes or agreed backup slides when appropriate; neither may conceal a limitation that changes an audience-visible conclusion. Do not add backup slides outside an explicit total count without agreement.

## Show representative designed samples

Before full production, show the proposed sequence and two or three designed sample slides unless the user chooses another preview process, delegates direction selection, or already approved equivalent samples. Select representative content layouts such as a mechanism, a result, and a comparison; a cover alone does not demonstrate the whole deck's design.

Produce actual sample slides and render them with the available presentation workflow. Show the images inline or through the supported artifact preview, alongside the proposed sequence. A textual style description or an image-generation prompt is not a designed slide. If sample rendering is unavailable, report the limitation and agree on a fallback rather than claiming samples were viewed.

Let the user accept or refine the sequence, text density, and visual direction before producing the rest. Ask through the popup when supported. Reuse accepted decisions; only revisit them when new source material or a requested change materially affects them. Continue independent source review while this choice is pending. Once selected, complete authoring and verification without approval at every internal step.

## Produce editable slides

Keep titles, body text, labels, tables, and quantitative charts editable in the chosen application. Use native text, tables, and charts where supported. Keep original data or a reproducible data source with quantitative displays. Do not flatten an entire slide into an image to achieve polish; a user-supplied screenshot or illustration can remain an image with editable surrounding text.

Use visuals to explain the topic. Source or generate illustrations when they clarify an idea; use actual project screenshots, photos, measurements, and plots for claims about the work. Generated illustrative imagery must not fabricate test results, implementation evidence, correct wiring, exact components, equations, or logos. Prefer editable diagrams when exact labels or connections matter, and validate those against sources. Cite external claims and assets in the appropriate slide or notes, with audience-visible attribution when required.

Follow the selected visual direction and template before generic defaults. Maintain readable hierarchy, spacing, and consistent typography without forcing every slide into the same layout. For Hebrew mixed with English, inspect actual text direction, punctuation, numbers, equations, and chart labels. Match the agreed text density; reduce repetition or split content before making text unreadably small.

## Verify and deliver

Follow the chosen presentation skill's export and validation workflow. Check requested coverage, source fidelity, slide count, approximate speaking time, notes, and editability. Render and inspect every final slide at readable size. Fix clipping, unintended overlaps, poor contrast, broken text direction, illegible labels, and diagrams or charts that disagree with their sources. Reinspect the saved revision after corrections.

Deliver the editable deck and requested notes or preview. Link the actual files or cloud artifact. State any material limitation, including unverified rendering, application compatibility, or physical project results. Never claim testing in an application that was not opened or that timing was rehearsed when it was only estimated. If verification is unavailable, deliver only an explicitly labeled draft unless the user made verified layout a condition of delivery.

Completion means the selected design and sequence are implemented in an editable deck, all applicable checks are complete, and remaining limitations are explicit. A plan, sample image, or flattened deck alone does not complete a request for the final presentation.
